# EcoHousingExporter

Server-side Eco mod foundation for Eco Housing V0.2.

The goal of this mod is to expose the exact data consumed by the web app from a live Eco server. The app should not scrape local server files and should not depend on unstable vanilla web endpoints for economy data.

This folder currently contains a buildable contract/core layer:

- DTOs matching the app's `eco-data.json` and economy schema;
- `IEcoHousingExportProvider`, the seam where live Eco data will be collected;
- `IEcoLiveDataReader` and `EcoDataSnapshotBuilder`, the bridge that turns live Eco registries into `/data`;
- `StubEcoHousingExportProvider`, which returns valid empty payloads with warnings;
- `EcoHousingHttpRouter`, a small endpoint router that can be connected to Eco's HTTP hook once the ModKit references are known;
- `EcoHousingEndpointBridge`, a testable registration bridge for the three exporter endpoints;
- `EcoHousingController`, an ASP.NET MVC controller exposing the same routes if Eco's web server discovers mod controllers;
- an `ECO_MODKIT` guarded adapter placeholder.

## API Contract

The mod must expose:

```http
GET /api/v1/eco-housing/status
GET /api/v1/eco-housing/data
GET /api/v1/eco-housing/economy
```

The exporter must also answer `OPTIONS` preflight requests and include CORS headers on every response, because the web app may be hosted on GitHub Pages or another origin:

- `Access-Control-Allow-Origin: *`
- `Access-Control-Allow-Methods: GET, OPTIONS`
- `Access-Control-Allow-Headers: Content-Type`

### `/status`

Returns server/exporter metadata:

```json
{
  "serverName": "Eco Server",
  "ecoVersion": "0.11.x",
  "exporterVersion": "0.2.0",
  "generatedAt": "2026-06-09T00:00:00.000Z",
  "endpoints": ["/api/v1/eco-housing/status", "/api/v1/eco-housing/data", "/api/v1/eco-housing/economy"],
  "warnings": []
}
```

### `/data`

Returns the same schema as `outputs/eco-data.json` generated by the local extractor:

- `housing`
- `items`
- `recipes`
- `skills`
- `roomCategories`
- `roomTiers`
- `worldObjects`
- `occupancy`
- `housingEquivalenceGroups`
- `constructionMaterials`
- `meta`

The data must represent the live server rules, including installed mods.
`constructionMaterials` maps each room material tier to the item classes that can be used for house construction pricing. The exporter may return server/mod-specific materials; clients fall back to vanilla defaults only when this field is absent.

When `/data` is produced by the current reflection provider, `meta.extractionCompleteness` describes which sections are reliable and which still need an Eco-specific collector. By default, recipes are `metadata-only`: the provider can detect recipe classes, required skill metadata, and a likely product, but it does not instantiate `RecipeFamily` constructors to read ingredients because constructors can register recipes and mutate server state. WorldObject room requirements are `partial-reflection`: room volume, room material tier, containment, occupancy component, and room-requirements component are read from attributes, while exact occupancy geometry and exact operational watt/fuel/water values need either source enrichment or a live collector.

The provider treats `/data` as stable for one EcoServer runtime. When the exporter DLL is loaded, a non-blocking startup warm-up builds the snapshot and stores it in memory. Later `/data` calls return the cached snapshot. If a user calls `/data` before warm-up completes, the endpoint still builds the fast reflection snapshot and then lets background enrichment replace the cache when available. Set `ECO_HOUSING_DISABLE_STARTUP_WARMUP=1` to disable startup warm-up while debugging.

The reflection provider can optionally enrich recipes from Eco mod source files. Set `ECO_HOUSING_SOURCE_ROOTS` to one or more source folders, separated by the platform path separator (`;` on Windows, `:` on Linux/macOS). For a standard Windows install, a useful value is:

```powershell
$env:ECO_HOUSING_SOURCE_ROOTS = "C:\Program Files (x86)\Steam\steamapps\common\Eco\Eco_Data\Server\Mods"
```

When source enrichment finds recipes, `meta.extractionCompleteness.recipes` becomes `source-code`. The parser reads common AutoGen patterns for `IngredientElement`, `CraftingElement`, `CraftingComponent.AddRecipe`, and `CraftingComponent.AddTagProduct`, so it can include ingredients, products, crafting tables, and variant base recipes without executing recipe constructors.

The same source roots are also scanned for `WorldObjectOccupancyAutoGen.cs`. When found, `meta.extractionCompleteness.occupancy` becomes `source-code`, and each `WorldObject.AddOccupancy<TObject>` block is converted to `blockCount`, `floorArea`, `width`, `depth`, and `height`.

Source enrichment also scans world object classes and occupancy ports for operational requirements. When found, `meta.extractionCompleteness.requirements` becomes `source-code`. The parser reads common Eco patterns for power consumption/production, mechanical/electric power type hints, fuel consumption and fuel tags, water input, sewage output, smog output, and chimney output.

The same pass reads presentation metadata from source attributes such as `LocDisplayName`, `LocDescription`, `NoIcon`, `IconUrl`, and `IconPath`. When found, `meta.extractionCompleteness.presentation` becomes `source-code`. `LocDisplayName` is stored as `localizedName.en`, because AutoGen sources provide the English localized base string. If XLF localization files are present under the same source roots, matching `source` / `target` entries are also added to `localizedName` by language code, for example `localizedName.fr`. CSV localization files are not used for this mapping yet because they do not carry the English source string on their own. A future live Eco registry collector should still replace source parsing where possible, but source enrichment is already useful for modded servers that ship readable `.cs` mod files.

Room categories and room tiers are currently included through a vanilla fallback copied from Eco's housing defaults. This keeps Room/House scoring usable in connected mode before the live housing-rule collector exists. A modded server that changes housing rules must replace this fallback through `IEcoLiveDataReader`; the fallback is marked with `ColorSource: "vanillaFallback"` and `meta.extractionCompleteness.roomCategories = "vanilla-fallback"`.

### `/economy`

Returns a normalized market snapshot:

```json
{
  "fetchedAt": "2026-06-09T00:00:00.000Z",
  "currencies": ["Credits"],
  "listings": [
    {
      "itemClass": "HewnTableItem",
      "quantity": 5,
      "price": 12.5,
      "currency": "Credits",
      "storeName": "Carpentry Store",
      "seller": "Player",
      "storeId": "store-entity-id",
      "sellerId": "seller-user-id",
      "taxRate": 0.05,
      "fee": 0
    }
  ],
  "warnings": []
}
```

The exporter normalizes sell offers before returning them:

- invalid offers are dropped with warnings;
- object class names are mapped to item class names when possible;
- identical listings from the same store/seller/currency/price/tax/fee are merged by summing quantity.

## Implementation Plan

- Wire the project to Eco server assemblies or ModKit references.
- Replace `StubEcoHousingExportProvider` with an Eco-backed provider.
- Register `EcoHousingEndpointBridge` with Eco's HTTP server or controller system.
- Keep the wire format stable; the web app validates the minimum schema and displays exporter warnings.

### Building with Eco references

The project builds without Eco assemblies for contract tests and development. When Eco reference assemblies are available, pass their directory through `EcoReferencePath`:

```powershell
dotnet build .\work\eco-housing-exporter\EcoHousingExporter.csproj `
  -p:EcoReferencePath="C:\Path\To\Eco\Server\Assemblies"
```

By default this imports `Eco*.dll` from that folder as non-copy-local references. If your ModKit uses another layout, pass `EcoReferencePattern`, for example `-p:EcoReferencePattern="*.dll"` for a folder that contains only managed reference assemblies. Avoid pointing this at a folder containing native Steam/runtime DLLs.

The `ECO_MODKIT` conditional code can then be enabled by the final Eco mod build pipeline once the real server endpoint hook is known:

```powershell
dotnet build .\work\eco-housing-exporter\EcoHousingExporter.csproj `
  -p:EcoReferencePath="C:\Path\To\Eco\Server\Assemblies" `
  -p:DefineConstants=ECO_MODKIT
```

### Packaging

Create a local package with:

```powershell
.\work\eco-housing-exporter\scripts\package-exporter.ps1
```

This builds the exporter in `Release`, creates `work/eco-housing-exporter/dist/EcoHousingExporter`, and writes `work/eco-housing-exporter/dist/EcoHousingExporter.zip`.

To package against Eco/ModKit references:

```powershell
.\work\eco-housing-exporter\scripts\package-exporter.ps1 `
  -EcoReferencePath "C:\Path\To\Eco\Server\Assemblies" `
  -EcoReferencePattern "*.dll" `
  -DefineEcoModKit
```

The package contains:

- `EcoHousingExporter.dll`;
- optional build artifacts such as `.pdb` / `.deps.json` when produced by the SDK;
- `README.md`;
- `eco-housing-exporter.manifest.json` with endpoint and build metadata.

### Installing on a local Eco server

For the current Steam server layout:

1. Build the package:

   ```powershell
   .\work\eco-housing-exporter\scripts\package-exporter.ps1
   ```

2. Install the package into the local Steam Eco server:

   ```powershell
   .\work\eco-housing-exporter\scripts\install-local-eco-server.ps1
   ```

   The installer rebuilds the package by default, copies only the precompiled DLL and web assets, and creates timestamped `.bak-*` backups if files already exist.

Manual install is also possible:

1. Copy the compiled exporter DLL:

   ```powershell
   Copy-Item .\work\eco-housing-exporter\dist\EcoHousingExporter\EcoHousingExporter.dll `
     "C:\Program Files (x86)\Steam\steamapps\common\Eco\Eco_Data\Server\Mods\EcoHousingExporter.dll"
   ```

Then restart `EcoServer.exe`.

Test the exporter:

   ```powershell
   .\work\eco-housing-exporter\scripts\test-exporter-endpoints.ps1
   ```

For a full local smoke test, you can let the script start `EcoServer.exe`:

```powershell
.\work\eco-housing-exporter\scripts\test-local-eco-server-live.ps1 -TimeoutSeconds 180
```

If EcoServer only starts correctly from Steam or an interactive console on your machine, start it manually first, then run:

```powershell
.\work\eco-housing-exporter\scripts\test-local-eco-server-live.ps1 -UseExistingServer -TimeoutSeconds 60
```

If this script reports that no new Eco log was written, EcoServer did not reach normal startup in that run. In that case validate from an interactively started server before debugging the exporter itself.

The experimental bootstrap attempted to use `HttpListener` and defaulted to:

```text
http://localhost:3012/api/v1/eco-housing/
```

If that bootstrap is ever made viable, another host or port can be configured with `ECO_HOUSING_EXPORTER_PREFIXES`. Multiple prefixes are separated with `;`:

```powershell
$env:ECO_HOUSING_EXPORTER_PREFIXES = "http://localhost:3012/api/v1/eco-housing/;http://*:3012/api/v1/eco-housing/"
```

Using `http://*:` may require a Windows URL ACL reservation. Start with `localhost` for local validation.

Do not install `UserCode/EcoHousingExporter/EcoHousingExporterBootstrap.cs` on current Eco 0.13 servers. Live testing showed Eco ModKit UserCode does not automatically reference the precompiled exporter DLL or `System.Net.HttpListener`, causing server startup to fail during mod compilation. The installable package does not include this bootstrap; the source remains in the repo only as historical investigation material.

### HTTP integration bridge

The Eco HTTP/controller hook is ASP.NET MVC application-part discovery. `Eco.WebServer.Web.Startup` calls `AddEcoMvcMods()`, which adds every assembly in `ModKitPlugin.LoadedManagedAssemblies` before `MapControllers()`. Because `EcoHousingExporter.dll` is loaded from `Mods`, `EcoHousingController` is discovered by Eco's existing web server on the configured `Network.eco` web port, usually `3001`.

Local live proof:

- EcoServer starts without the UserCode bootstrap.
- Logs show `Loading EcoHousingExporter...`.
- `GET http://127.0.0.1:3001/api/v1/eco-housing/status` returns 200.
- `GET http://127.0.0.1:3001/api/v1/eco-housing/data` returns live reflection data.
- `GET http://127.0.0.1:3001/api/v1/eco-housing/economy` returns a valid economy payload, with warnings when no listings are detected.
- `GET http://127.0.0.1:3001/eco-housing` serves the packaged app.

To avoid guessing that API in the app contract, the exporter now exposes a small bridge:

```csharp
public interface IEcoHousingEndpointHost
{
    void RegisterEndpoint(string path, Func<string, EcoHousingHttpResponse> handler);
}
```

An Eco-specific adapter only needs to implement this host against the real server hook, then call:

```csharp
EcoHousingEndpointBridge.Register(host, provider);
```

This registers the three stable paths and forwards the incoming HTTP method to `EcoHousingHttpRouter`, including `OPTIONS` preflight handling.

For standalone host tests or future hosts that expose an ASP.NET Core endpoint builder, the exporter also provides a direct adapter:

```csharp
app.MapEcoHousingExporter(provider);
```

or:

```csharp
endpoints.MapEcoHousingExporter(new EcoHousingHttpRouter(provider));
```

This adapter is smoke-tested by starting a real local ASP.NET Core server, then calling `/api/v1/eco-housing/status`, `OPTIONS /api/v1/eco-housing/data`, and `POST /api/v1/eco-housing/data`.

The exporter also includes a normal ASP.NET MVC controller:

```csharp
services.AddControllers()
    .AddApplicationPart(typeof(EcoHousingController).Assembly);

app.MapControllers();
```

`EcoHousingController` serves:

- `GET|OPTIONS /api/v1/eco-housing/status`;
- `GET|OPTIONS /api/v1/eco-housing/data`;
- `GET|OPTIONS /api/v1/eco-housing/economy`.

`EcoHousingAppController` serves the packaged static app from `Mods/EcoHousingExporter.Web`:

- `GET /eco-housing`;
- `GET /eco-housing/*`.

The controller uses `EcoHousingExporterRuntime.Provider`, which defaults to `ReflectionEcoHousingExportProvider`. A real Eco adapter can swap the provider during server startup:

```csharp
EcoHousingExporterRuntime.UseProvider(new ReflectionEcoHousingExportProvider(
    assemblySource: () => AppDomain.CurrentDomain.GetAssemblies(),
    economyReader: liveEconomyReader,
    dataReader: liveDataReader));
```

This MVC path is smoke-tested with a real local ASP.NET Core server and is the first integration path to try if Eco's `WebServerPlugin` loads controller application parts from mod assemblies.

### `/data` collection targets

The Eco-backed provider should collect data from live registries/state, not from source files:

- item definitions and tags;
- recipes and recipe products/ingredients;
- skills/professions;
- `HomeFurnishingValue` / housing config;
- room categories and room tiers;
- world object requirements and occupancy;
- variant/equivalence relationships;
- localized names and icon URLs when accessible;
- loaded mods metadata when accessible.

Current reflection support already collects a safe subset from loaded assemblies and optional source roots:

- item classes and basic item metadata;
- housing item values when exposed as static `homeValue` / `HomeValue`;
- skill classes;
- recipe classes, required skill attributes, and likely product item classes;
- recipe ingredients, products, crafting tables, and `AddTagProduct` variant base recipes when `ECO_HOUSING_SOURCE_ROOTS` points at readable Eco mod source files;
- world object occupancy dimensions from `WorldObjectOccupancyAutoGen.cs` in those source roots;
- operational requirements from world object source classes and occupancy ports in those source roots;
- presentation metadata from `LocDisplayName`, `LocDescription`, `NoIcon`, icon path attributes, and XLF localized names in those source roots;
- variant annotations derived from `RecipeDto.VariantBaseRecipeClass`;
- equivalence groups derived from housing value, room limit, diminishing rules, surface/attachment tags, room requirements, and occupancy dimensions;
- vanilla fallback room categories and room tiers.
- world object room requirements from attributes such as `RequireRoomVolume`, `RequireRoomMaterialTier`, `RequireRoomContainment`, `OccupancyRequirementComponent`, and `RoomRequirementsComponent`.

It intentionally does not instantiate recipe families or world objects. The next Eco-specific data reader must read live registries/components instead, so room rules, exact runtime-generated requirements, and any recipes generated dynamically at runtime come from server state without constructor side effects.

The buildable bridge for this work is:

- implement `IEcoLiveDataReader` against live Eco registries;
- fill `EcoLiveDataSnapshot` with item, recipe, skill, housing, room, world-object, occupancy, and equivalence data;
- let `EcoDataSnapshotBuilder` normalize sorting, duplicate removal, `meta.generatedAt`, `meta.counts`, variant annotations, and equivalence groups;
- keep source-specific warnings in the snapshot so the app can surface incomplete server data.

### `/economy` collection targets

The economy provider should inspect placed store-like world objects and normalize their active sell offers:

- item class;
- quantity available;
- unit price;
- currency item/name;
- store name;
- seller/player;
- stable store/seller ids if Eco exposes them;
- tax or fee fields if Eco exposes them.

If a field cannot be read on a server version, return a warning and keep the rest of the snapshot usable.

Current Eco source hints from the local installation:

- placed stores are `StoreObject` / `WoodShopCartObject`;
- both require `Eco.Gameplay.Components.Store.StoreComponent`;
- store objects also use Eco economy/currency namespaces such as `Eco.Gameplay.Economy`;
- Eco's web server discovers mod MVC controllers through `AddEcoMvcMods()`.

Current exporter bridge:

- `EcoEconomySnapshotBuilder` normalizes, validates, sorts, and merges offers.
- `ReflectionEcoLiveEconomyReader` can convert live store-like objects into `EcoLiveStoreOffer` entries through reflection.
- `EcoWorldStoreObjectSource` resolves the live `WorldObjectManager` plugin, enumerates `WorldObjectManager.All`, selects objects with `StoreComponent`, and passes those components to `ReflectionEcoLiveEconomyReader`.

The reflection reader searches readable store/offer/listing/trade members and extracts common fields such as `ItemClass`, `Quantity`, `UnitPrice`, `Currency`, `StoreName`, `Seller`, ids, tax, and fee. It handles Eco-style `StoreData.SellOffers`, `TradeOffer.Stack.Item`, `TradeOffer.Stack.Quantity`, store-level currency, and ignores buy offers. When the store object is an Eco `StoreComponent`, it also reads parent `WorldObject` metadata such as `Name`, `NameOfCreator`, and `ObjectID`. It is intentionally tolerant because Eco server versions and mods may wrap store offers differently. Any unreadable or invalid offer is dropped with a warning instead of failing the whole endpoint.

It also handles dictionary-like store data such as `Dictionary<ItemType, Listing>` and nested price objects such as `Price.Amount` plus `Price.Currency`. This keeps the exporter contract stable even if the Eco adapter receives offers from a registry shape that is not a flat DTO.

The remaining validation work is:

- test `/economy` on a world that contains real player stores, currencies, and active sell offers;
- compare the normalized quantities/prices against the in-game store UI;
- extend the reflection reader if that world exposes taxes, fees, or modded offer shapes through different member names.

This keeps Eco-specific reflection/API code isolated from the stable wire contract used by the web app.

## Implementation Notes

- Keep the wire format stable; the web app validates the minimum schema and displays exporter warnings.
- Prefer exposing already-normalized item class names (`HewnTableItem`) so the web app can match market data to `eco-data.json`.
- If a server cannot expose a field, return a warning instead of omitting the entire endpoint.
